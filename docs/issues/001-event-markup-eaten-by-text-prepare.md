# 001 · 文本预处理会吃掉事件标记（顺序反了）

**状态**：已修复（`agentic_tts/engine.py::_plan`）
**发现**：2026-09-07，S5 门面首跑
**影响范围**：所有带 `[pause:...]` / `[laugh]` 标记的输入

## 现象

第一版 `_plan()` 的顺序是「预处理 → 解析事件标记 → 分段」，实跑：

```
输入：今天的人工智能资讯，[pause:500ms]第一条：模型发布了。[laugh] 很有意思。
实际送进模型：今天的人工智能资讯，[pause:五百毫秒]第一条：模型发布了。很有意思。
chunks = 1（应为 2）
```

**数字规范化把标记内部的 `500ms` 改写成了「五百毫秒」**，于是事件正则再也匹配不上：

- 停顿悄悄消失（`chunks=1`，没有插静音）；
- 而 `[pause:五百毫秒]` 这串字符**留在了稿子里**，会被模型逐字念出来。

`[laugh]` 那条侥幸生效，只因为它里面没有数字。Markdown 与 URL 规则同理会啃掉标记
（`[文字](url)` 的处理逻辑本来就在剥方括号）。

## 判定

不是"数字规范化写错了"——它做的正是分内的事。**是流水线顺序错了。**
标记属于"控制信息"，预处理属于"内容清洗"，控制信息必须在内容被改写之前解析出来。

## 修法

`_plan()` 改成：**解析事件标记 → 逐片段预处理 → 分段**。

```python
pieces, warnings = parse_events(req.text, ...)     # 先把控制信息取出来
for piece in pieces:
    piece.text = prepare(piece.text, options)      # 再清洗内容
```

顺带一个好处：预处理后变空的片段（整段只有 URL）会在这一步被丢掉并记 warning，
而不是送一个空字符串进模型。

## 回归用例

`tests/test_text.py::test_number_normaliser_would_eat_the_markup` ——
它**同时断言两件事**：预处理确实会改掉标记（所以顺序不能反），以及正确顺序下能切成 2 段。
只断言"现在是对的"挡不住有人为了别的原因把顺序调回去。

## 教训（写给后来接引擎的人）

事件标记这类控制信息**不要指望它能穿过文本清洗链路**。本模块的约定是：
控制信息在最前面被解析掉，之后流水线里流动的一律是纯内容。
引擎拿到的 `SynthChunk.text` 已经没有任何标记（除非引擎声明了原生 `VOCAL_EVENTS`，
那时门面会刻意把标记留下来交给它）。
