# 003 · 失控启发式判据与「慢语速 instruct」会互相踩

**状态**：已知行为，暂不改默认值（可配置）
**发现**：2026-09-07，真实权重跑 `samples/segments.yaml` 时
**影响范围**：`guard.duration_ratio`（辅助判据），只影响是否多花一次生成

## 现象

样例第 3 段：

```
文本（14 字）：这项技术的落地速度超出预期。
instruct：沉稳的中年女声，语速偏慢，语气克制
→ 首次生成 10.4s
→ 判定：时长 10.4s 超出预期 2.8s 的 3 倍 ⇒ 疑似失控，换种子重试
→ 重试得到 5.36s，通过
```

日志（实测）：

```
WARNING [agentic_tts.module] 疑似失控（时长 10.4s 超出预期 2.8s 的 3 倍（14 字）），换种子重试 1/1
```

## 判定：这次算「拦对了」，但判据确实偏紧

- 14 字 10.4s ≈ **0.74 秒/字**，就算「语速偏慢」也远超正常范围（正常约 0.2 秒/字），
  所以这一次的重试是合理的，重试后的 5.36s 也更像正常朗读。
- 但辅助判据的算式是 `字数 / 5 × 3`，**它不知道 instruct 里写了「语速偏慢」**。
  实测过 instruct 能把时长拉开 30–42%，如果再叠加「逐字强调」这类指令，
  一条正常音频完全可能撞上 3 倍线，代价是白跑一次生成（CPU 上几十秒）。

主判据（撞 `max_new_tokens` 换算的时长上限）不受影响 —— 那一条是硬事实。

## 怎么处置

**不改默认值**：宁可偶尔多跑一次，也不要把真失控放过去（失控音频是几十秒噪声、
不报错、波形指标和静音检测都测不出来）。需要时按场景调：

```yaml
guard:
  duration_ratio: 4.0     # 大量使用慢语速/强调类 instruct 时放宽
  chars_per_sec: 4.0      # 或者直接把语速估计调慢
  retry: 1                # 重试次数；0 = 只判定不重试
```

判成失控时 `SegmentResult.retries` 会记下来，`warnings`/日志里写清是哪条判据命中的 ——
**先看日志再调参数**，不要凭感觉动。

## 待办（需要 4060）

在 GPU 上跑一批「不同 instruct × 同文本」，统计秒/字的分布，
再决定要不要把辅助判据改成「按 instruct 是否含语速词做分档」。
CPU 上一条几十秒，这种扫描不该在开发机上做。
